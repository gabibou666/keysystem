DEVELOPER GUIDE

Publish your script. Set up access.

Use this guide to publish a Lua script, give a user a license and test your project loader. Each project has its own source, licenses, checkpoint settings and private API token.

01. Create your project

  1. Create your account with Google, Discord or email, then open the dashboard. Email accounts must verify their address first. Use the same sign-in method to return to your workspace.
  2. Choose New project and name your script. Save the API token shown after creation if you plan to issue licenses from your own backend. You can manage licenses in the dashboard without using that token.
  3. Open Script hosting, paste your source or upload a Lua or Luau file up to 1 MB. Choose Universal or One Roblox game; for one game, paste its Roblox link or enter its Place ID. Publish to check and obfuscate the release before it becomes available.
  4. Open Licenses, choose a duration and issue a test key. Copy or download the full key before closing the result.
  5. Open Integration and copy your project loader. The included GUI asks for the test key in-game. With the standard key loader, replace YOUR_LICENSE with that key; connect a personal GUI using the SDK below. Test before sharing it.

What to share with your users

Share the project loader and a project license. If you use checkpoints, share the public key page from the Checkpoints tab so users can obtain their own key. They do not need a developer account. Keep project API tokens and provider credentials in your workspace or backend.

02. Run the loader

The loader sends a project-specific license check before retrieving the published build. If device binding is enabled, the first successful check binds the license to that device. The executor needs HTTP requests and loadstring support.

getgenv().AUDIT_KEY = "ah_YOUR_LICENSE"
loadstring(game:HttpGet(
  "__SITE__/api/platform/v1/loader/PROJECT_UUID"
))()
Never distribute your API token. Keys start with ah_. Server API tokens start with ahp_ and belong only on your backend.

Checks, free obfuscation and game targeting

Each upload is parsed locally as Lua/Luau, transformed with the pinned darklua build tool, and parsed again. Publication rechecks the saved build. Invalid code, failed builds or an unavailable build tool leave the previous version unchanged; the site never silently publishes the original as a fallback. Scripts are not executed during these checks.

Obfuscation uses local-variable renaming and compact output. It is free without paid credits or a monthly build quota. Size, request and concurrency limits protect service availability. This is lightweight obfuscation, not encryption or a guarantee against copying. Syntax checks cannot prove that a script is safe or works with every Roblox game and executor; test the resulting release in its intended environment.

Universal adds no game restriction. One Roblox game checks the exact game.PlaceId before running the script. Use the number in the Roblox URL after /games/. It does not cover other places inside the same Roblox experience automatically.

Publish the next version

Return to Script hosting and publish the updated source. Publishing replaces the current version; the project loader URL stays the same. Users receive the new version on their next successful load. Already running scripts are not updated automatically. Keep your own source backups if you need previous releases.

Choose a key interface

When publishing a licensed script, use Choose key interface, colors and buttons, or open Script hosting, then Key interface for your selected project. Choose My own GUI / library or AUDIT HUB interface, then save. You can change the interface without uploading your source again or changing the loader URL.

The included interface offers Compact, Card and Sidebar presentations, five accent colors, and Small, Medium or Large buttons. The dashboard preview updates immediately. These are bundled native Roblox GUI presentations; no external library is fetched. The preview is illustrative, so test the actual loader in your executor.

With the included interface, users run this loader without editing a key. The GUI prompts for their license, validates it on the server and launches the script only after validation and compilation succeed.

loadstring(game:HttpGet("__SITE__/api/platform/v1/loader/PROJECT_UUID"))()

Get a key copies the project's checkpoint page when configured. If the project uses manually delivered licenses, give users their key yourself. Free catalogue releases skip the key interface.

Connect your own GUI or library

Choose My own GUI / library. Keep your existing library and replace its key button callback with the client SDK below. This works with any library that can read a text value and call a Lua function. Replace PROJECT_UUID with your project's ID from Integration.

local client = loadstring(game:HttpGet(
    "__SITE__/api/platform/v1/sdk/PROJECT_UUID"
))()

-- Use this callback in your existing library's Validate button.
local checking = false
local function submitKey(keyText, showStatus, closeKeyGui)
    if checking then return end
    checking = true
    showStatus("Checking your key...")
    local ok, reason = client.load(keyText)
    checking = false
    if ok then
        closeKeyGui()
    else
        showStatus(tostring(reason or "Key rejected. Try again."))
    end
end

Example with an existing Roblox GUI

Use your own TextBox, TextButton and status label. Call submitKey from your library's button callback, or connect the native button below. The SDK performs the HTTP request and supplies a stable device identifier.

validateButton.Activated:Connect(function()
    submitKey(keyInput.Text,
        function(text) statusLabel.Text = text end,
        function()
            keyInput.Text = ""
            keyScreenGui:Destroy()
        end
    )
end)

getKeyButton.Activated:Connect(function()
    local url = client.getKeyUrl()
    if not url then
        statusLabel.Text = "Ask the developer for your license."
    elseif type(setclipboard) == "function" then
        setclipboard(url)
        statusLabel.Text = "Key page copied. Open it in your browser."
    else
        statusLabel.Text = url
    end
end)

client.validate(key) checks a license and returns a table with success and reason/error; it does not retrieve or run the script. client.load(key) validates again, retrieves the build, compiles it and schedules execution; it returns true on successful validation/compilation or false, reason on failure. These functions use dot calls, not colon calls. A successful result does not certify the script's later runtime behavior.

Do not bundle the protected script inside your key GUI. Host it separately in Script hosting and let client.load retrieve it after server validation. A client-side success flag is not an authorization mechanism. Never put the private project API token in any GUI or Lua source; the SDK uses only the player's license.

The project loader and SDK are public, so include only UI code and public project IDs in your GUI. Keep entered keys out of logs, shared screenshots, URLs and public configuration files. See Roblox button documentation for native button events.

03. Validate a license

Send a JSON POST request to /api/platform/v1/check. No API token is required: the license is the credential. A key from another project is rejected.

POST /api/platform/v1/check
Content-Type: application/json

{
  "projectId": "PROJECT_UUID",
  "key": "ah_YOUR_LICENSE",
  "hwid": "your-stable-device-identifier",
  "executor": "YourExecutor",
  "loadScript": true
}

On success, the response contains success: true, expiresAt, and, when loadScript is true, script and version. The first successful check binds a device when binding is enabled. Failed checks do not bind a device.

{
  "success": true,
  "expiresAt": "2026-10-10T12:00:00.000Z",
  "version": 1,
  "script": "-- your verified, obfuscated Lua build"
}

04. Issue keys from your backend

Use the project's API token as a Bearer credential. A token can issue licenses only for its own project. Rotating it in the dashboard invalidates the previous token immediately.

POST /api/platform/v1/projects/PROJECT_UUID/licenses
Authorization: Bearer ahp_YOUR_PRIVATE_TOKEN
Content-Type: application/json

{
  "durationHours": 24,
  "count": 1,
  "note": "Order reference"
}

The response contains a licenses array with each full key, license id and expires_at. Store these keys securely before delivering them to your users.

Publish a script

  1. Create a project and save its Lua source in Script hosting.
  2. Open Publish scripts. Select the project, then enter a public title, description and game.
  3. Choose With a license / checkpoints or Free access, without a key, then publish.
  4. Your script appears directly in the script catalogue. Share its own page with users; they can read the description and copy the loader.

You do not need to create a hub. A developer profile is created automatically with your first publication. You can customize it in the optional profile settings, and visitors can use it to find your other scripts. Private projects and drafts are not listed. The game restriction comes from the saved release in Script hosting; the optional game name is only a public label.

Free access publishes the executable build. Anyone can download or copy that release. Later private uploads do not replace it until you choose Update public release. Unpublishing stops future access through the site but cannot erase copies already downloaded.

Licensed releases retain the project license check. Configure checkpoints to offer Get a key, or deliver licenses yourself. Making an existing developer profile private hides its publications. Publishing another script does not undo a profile privacy choice.

Safety, profiles and moderation

When publishing a script, declare mobile support as Yes, No or Not declared. The public page shows this declaration and whether platform access requires a key. In your public developer profile, choose a name, address, description and avatar theme, and optionally add a HTTPS Discord invite and website. Your community appears on your profile and script pages. Invite and website destinations are third-party services.

Every upload is analyzed locally before and after obfuscation, without executing its code. High-risk findings refuse the new release. Suspicious or opaque behavior queues it for review and leaves the previous active version unchanged. Keep your readable source and review dependencies before uploading: already obfuscated code or remote loaders can conceal behavior. No analysis or approval guarantees that a script is harmless.

Signed-in users can report a public script from its page. Describe the behavior without license keys, passwords or source code. Authorized moderators open /moderation to approve or reject held builds, resolve reports, quarantine an exact active version and inspect the paginated audit journal. A quarantined project cannot deliver its script through public free or licensed endpoints. A replacement requires review; a free listing must be explicitly republished afterward.

Only administrators grant moderator roles. Account signup and profile editing cannot assign these permissions. Moderation displays metadata and findings, not private source. The audit journal covers new platform actions and decisions, with sensitive input excluded; it does not reconstruct past or infrastructure logs.

05. Configure checkpoints

Choose a provider, enter its credentials, and connect it. The dashboard shows its callback and a separate public key page for users. Optional task settings are collapsed. Saved credentials do not need to be entered again.

Share the public key page with users. Callbacks handle verification and do not replace the key page. Start and finish in the same browser and on the same network. Sessions last 30 minutes. Changing networks requires a new checkpoint.

LootLabs

  1. Paste your creator API token. One task is the default; choose up to five in optional settings.
  2. Copy the private callback into Advanced → Postback. Keep its secret parameter.
  3. Enable click_id, unique_id and ip. The link's puid identifies the session; each unique task receipt advances it.

The callback remains available after reloading. Switching providers invalidates it. Official postback guide · Link creation API.

Work.ink

Paste your link and its numeric dashboard link ID. The callback ends in ?token={TOKEN}; keep that macro when setting a destination. We override the destination for each session, check the returned token's expiry and link ID, and consume it once.

Official key system guide · Destination override API.

Linkvertise

Copy the destination shown in the connection form. Create a Target Link with that destination, then paste its link and your 64-character anti-bypassing token. The callback stays visible after saving. Paste-Links are unsupported. Anti-bypassing affects all your Target Links; prepare their destinations first. The returned hash lasts ten seconds and is verified immediately on the server.

Official anti-bypass documentation (PDF).

LinkUnlocker

Paste your unlock link and 64-character Redirect API token from User settings → Api Keys. We encrypt a fresh destination containing a private session proof. The dashboard shows the return endpoint; do not use that base URL alone as a complete destination. The proof and encrypted destination must validate before issuance.

Official Redirect API guide.

Test your setup

Choose Test as a user, complete the provider flow, and confirm that a key is issued. Keep credentials and the LootLabs callback private. Re-test after changing settings. Automated tests simulate providers; they do not confirm your live account configuration.

A user cannot get a key or load the script

  1. Check that the key and loader belong to the same project. A valid key from another project will not work.
  2. Confirm that the project has a published script and that the license is active. Check the latest validation events under Integration for the rejection reason.
  3. For a changed device, reset the license device binding from Licenses. The next successful check binds it again.
  4. For a checkpoint, start on the public key page and complete the provider flow in the same browser and on the same network. If the session expired or verification failed, start a new checkpoint.
  5. Check the provider token, link ID, destination or postback settings against the provider-specific instructions above.

07. Limits and storage

  • 10 projects per developer account.
  • 10,000 licenses per project, including expired or revoked licenses.
  • 1–50 licenses per issuance request; duration from 1 to 8,760 hours.
  • One current published script per project, up to 1 MB.
  • Dashboard lists the latest 100 licenses and 30 validation events.
  • 120 platform requests per minute per client IP. Checkpoint sessions last 30 minutes.

Scripts and provider tokens are encrypted at rest. API tokens and license keys are stored as hashes. Completed checkpoint keys are temporarily encrypted so the originating browser can recover them during the session.
