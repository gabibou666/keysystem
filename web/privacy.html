Privacy Policy

Updated October 3, 2026.

Developer Workspace Data

Developer accounts store a display name and an internal account ID. Google and Discord sign-ins store the provider, its account identifier and a normalized verified email address for new accounts. Email accounts store the normalized email address, verification status and a password hash; plaintext passwords are not retained. Email verification and password recovery messages are sent through Resend when configured. Social identities are not automatically merged by email address.

Workspaces store project settings, license hashes and prefixes, license expiry and revocation state, and device identifiers hashed within each project. Uploaded Lua source and checkpoint provider tokens are encrypted at rest. Full manually issued license keys and project API tokens are shown once; their hashes are retained for validation.

Public profiles, safety review and moderation

Your chosen display name, profile description, avatar theme, Discord invite and website are public when your developer profile is published. Mobile support is a developer declaration. The catalogue indicates whether the platform requires a license; an independently embedded key system may differ.

New uploads undergo local static analysis before and after obfuscation. The server does not execute them or submit them to an external scanning service. Detected high-risk behavior blocks activation; opaque or suspicious builds are held for moderator review while the previous active release remains unchanged. Automated checks and moderator approval cannot guarantee safety, especially for externally loaded or obfuscated behavior.

Authorized moderators access release hashes, rule identifiers, held-release status, reports and application audit records through a restricted workspace, without private source or credentials. Report text and decision notes are limited and known credential formats are redacted; never submit keys, passwords or private code in a report. Audit records retain account identifiers, action names, project identifiers, release versions, hashes, rule identifiers, sanitized decision notes, role changes, timestamps and response status where available. Reports, review decisions and audit records are retained to operate moderation; there is currently no automatic expiry for these records. The journal begins when this feature is enabled and cannot reconstruct previous actions. General HTTP event recording is best effort and excludes raw bodies, credentials and IP addresses; it is not a complete infrastructure log.

Script content and access

Other developers cannot browse your private project or its uploaded source through their workspace. The public catalogue shows only the release details you choose to publish and your public developer profile. Account emails, provider credentials, private project descriptions and license management data are excluded from public catalogue responses.

Free access deliberately makes the released script available to anyone. Licensed access delivers it after a valid license check. Anyone receiving executable code may inspect or copy that delivered code; obfuscation does not make it secret. Unpublishing prevents future catalogue access, but cannot erase copies already downloaded.

The service processes script content on its servers to store and deliver it. Encryption at rest protects stored records, but the server holds the decryption keys. We cannot claim that site operators with privileged infrastructure access are technically unable to read script content. No public or developer workspace interface provides access to another developer's private uploads.

For new uploads, the server checks and obfuscates the code locally without sending it to a third-party obfuscation service. Only the resulting executable build is saved, encrypted at rest. The original is processed in memory and temporary build files, which are removed when processing finishes or fails. Older encrypted uploads are retained until replaced; they must be uploaded again before delivery through the new build process. A syntax check does not certify that a script is safe or functional in every game.

If you enter a license on a public script page, the page keeps it in memory without adding it to the address or browser storage. Copying your prepared loader deliberately places that key on your clipboard; do not share that loader. Sensitive input fields are cleared when leaving the page.

Project validation history records the executor name, result and time, and is removed after 90 days by the daily cleanup. Checkpoint sessions use a browser-specific cookie lasting 30 minutes. Completed checkpoint keys are encrypted for recovery by the originating browser during that session; session records and task receipts are removed by the daily cleanup after one day. Checkpoint sessions store an HMAC of the originating IP, not the raw address, to verify the same network at return and key recovery. A separate global register retains hashes of consumed provider proofs and consumption times to prevent reuse across projects after session deletion; it stores no raw proof, IP, account or project identifier. Developer account, project, script and license records are retained to operate the workspace, including expired or revoked licenses.

Developer registration uses a signed browser cookie (ah_registration), lasting up to 180 days, and keyed hashes of the browser identifier and IP address to limit repeated account creation. These quota records expire after 30 days of inactivity. No hardware fingerprint is collected.

Developer Discord sign-in requests identity and email access to prevent duplicate registrations. Google sign-in requests basic profile and email access. Essential developer session cookies last up to seven days; OAuth state cookies last ten minutes. Verification and password-reset tokens expire after one hour and are stored hashed. Expired sessions and email tokens are removed by daily cleanup. Signing out revokes the current session; resetting a password revokes all sessions for that account. Developers configure their own checkpoint provider accounts and are responsible for how they distribute and manage project access.

Central Discord bot administration

If the operator configures a central bot connection, authorized platform administrators can view its bot name, connection status, server names, server IDs, member counts, channels, categories and roles. Bot server settings are read from and saved to the bot's separate database. Credentials stay on the servers and are excluded from browser responses. Settings changes are recorded by administrator account ID and Discord server ID without welcome-message content. Ordinary developers and website moderators cannot access this global bot administration. Discord verification does not grant website staff roles.

Third-party services

Google and Discord provide optional sign-in. Resend sends account emails when configured. Developers may use LootLabs, Work.ink, Linkvertise or LinkUnlocker for checkpoints; visiting their sites is subject to their own privacy policies. No advertising script is loaded on this site.

HTTP security

HTTP rate limiting temporarily tracks resolved IP addresses in process memory. Registration quotas retain keyed hashes, and device binding stores project-specific hashes. Diagnostics omit credential-bearing URL parameters and raw error messages.

4. Your Rights Under GDPR

Under Articles 15 to 22 of the GDPR, you have the following rights regarding your personal data:

  • Right of access: You can request confirmation of whether personal data concerning you is being processed.
  • Right to rectification: You can request the correction of inaccurate data.
  • Right to erasure ("Right to be forgotten"): You can request the deletion of your personal data.
  • Right to restriction and objection: You can object to or limit the processing of your data.

To exercise any of these rights, contact us via our official Discord community server or contact our team through the AUDIT HUB platform.
